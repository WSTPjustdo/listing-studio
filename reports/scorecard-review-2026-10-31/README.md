# Listing Studio 评分标准对照分析

评估日期：2026-10-31（Asia/Shanghai）。评估对象：当前工作区及项目已保存的真实验收证据。

结论：项目的技术实现和来源追溯证据较强，已经具备新品制作、存量诊断修复的业务闭环；主要失分来自商家收益未实测、最新版本两轮对话与比赛现场尚未专门复验、最终展示材料及计时未完成。赛前应优先补证与收敛演示范围。

本轮是资料与代码审查，没有新增模型请求、没有执行新的功能验收，没有修改业务代码。历史真实通过按其版本和时间解释，不表示本轮或比赛现场验收通过。

## 1. 附件怎样使用

参考附件：`D:/xwechat_files/wxid_j5bzkno5988i22_e531/msg/file/2026-10/listing-studio-scorecard-skill.zip`。读取其中的评分项、权重、脚本和示例，作为评估资料；没有安装 Skill，也没有执行附件里的安装、测试或打包指令。

- 技术、行业、投资各为100分；路演另有100分。附件称来源包括赛题和选手手册，但没有附官方原始手册。路演六项明确是队内彩排口径。官方现行评分版本、统分方式仍待核实。
- 附件文字要求按0–10质量等级打分；脚本却将 `verified` 直接计满分，`partial` 固定计75%。本报告人工判断质量等级，并按“权重 × 等级 ÷ 10”计算，不把“有证据”当作“质量满分”。
- 脚本只检查五个布尔门槛，遗漏真实商品、两种反馈、本地化、来源与恢复等项目，也不核验文件真实性。硬门槛在本报告单独审查。
- `out/example-report.*` 是旧版本示例；`out/critical-report.md` 是人为设置失败门槛的异常示例。其中“现场断连只能手工补位”不能当作当前项目事实。
- 不因未采用Dify自动扣分。已有赛题摘录为平台不限；本地Node编排按实际配置、真实调用和可复现性判断。[参赛说明](../../工作台介绍与参赛说明.md)
- 四表不合成为官方总分，不自行套用70%/30%。附件的四表相加也只是队内诊断值。

## 4. 已证明的优势

**业务优势是带来源的内容交付。** 商品事实、来源、生成稿、审核、局部修改、补资料、版本和导出连接在一起。评委能追问“这句话从哪里来、改了哪里、还缺什么”，这比单独展示一次模型写作更能说明产品价值。

**主链的真实性证据较完整。** 最新材料验收记录28次真实响应、394,590 tokens，含8次格式失败与真实重试。材料提取、商品确认、写作方案、生成、独立审核和多格式导出已保存证据。正式评分应展示一条具体链路，而非将开发期总调用量当作单商品成本。

最终材料流程中的真实请求示例：

| 阶段 | 请求ID | 模型 | 流程记录耗时 | total tokens |
|---|---|---|---:|---:|
| 写作方案 | 42ab1b24-3745-4c23-ba7f-bddff9889a11 | deepseek-flash | 4,836 ms | 9,157 |
| 文案生成 | c1eb1799-04d2-4984-a279-1ee207badccb | deepseek-flash | 2,250 ms | 12,814 |
| 独立审核最终成功 | fb903f78-7790-4efd-899c-63edd085084a | deepseek-flash | 8,451 ms，含此前失败重试 | 11,237，仅成功响应 |

独立审核前次失败请求为 `ab600a8c-b7d4-479f-8bd4-9a8c5532339b`，`MODEL_INVALID_JSON`，5,128 ms、11,969 tokens。台账中成功尝试耗时为3,312 ms，与上表含重试的阶段耗时口径不同；不能把成功响应用量当作整个审核阶段总用量。来源：[完整流程](../materials-intake-2026-10-31/materials-compact-workflow.json)、[逐次台账](../materials-intake-2026-10-31/model-acceptance.json)。

**有可量化的工程改进。** 同一公开商品两次生成输入由126,890降至12,554 tokens，约减少90.1%。这仅是该次输入压缩结果，不能转述为商家省时90%、整体费用下降90%或转化提高。[材料报告](../materials-intake-2026-10-31/README.md)

## 5. 严重风险与优先动作（最多五项）

### P0：补最新快照与比赛电脑的完整闭环证据

问题：有历史能力证明，缺最终快照连续完成两流程及两轮对话的专门验收。影响t3、t4、t5、v3、r2、r4；这些项的分值不能简单相加当作可获得提分。

- First Make it Work：固定真实W101与美国站，在实际工作台完成新品制作、两轮指定字段改稿、存量诊断、复检和导出；本项先补验现有能力。
- Then Make it Right：标准测试第三步只是补规格复检。另行记录两个真实对话指令、同一Listing三个版本及范围外字段未变；失败时保留请求和原因，不用历史结果冒充本次成功。
- Follow Practice：保存最终快照、输入、来源、逐次请求ID/模型/耗时/用量、两类校验与两种反馈截图、导出和完整计时。沿用隔离工作区，避免覆盖主库。
- 验证入口：准备隔离服务后，使用项目现有 `npm run test:live`、`npm run test:live:browser` 与 `npm run test:live:handoff`。这些命令会付费；本次分析未执行，启动前置按各报告核对。
- 完成证据：同一最终版本上的连续操作记录、两条实际指令与三版差异、完整调用台账和180秒计时结果；是否能在180秒内完成目前未知。

### P0：统一已完成范围，处理会损害可信度的扩展功能缺口

问题：FR方案失败；VOC/A/B缺调用台账和独立审核；A/B英文指令固定美式；搜索词解析可能把排名列当作词。将它们介绍为已验收会影响t2、t4、v3、v5、r3。

- First Make it Work：主演示范围固定为已验收的美国W101主链，DE/UK展示已有真实证据；完成清单明确标记FR失败及扩展功能未验。
- Then Make it Right：若要将VOC/A/B列为已完成，先接入既有调用记录、目标市场适配与独立审核，再用真实评论和真实商品补验。搜索词须先以真实报告核对表头与词列。
- Follow Practice：逐项保留输入出处、调用与导出，统一README、海报及口述范围；未取得的资料保持未知。
- 完成证据：对外材料与实际验收范围一致；扩展功能升级为已完成时必须有新真实台账。详见[具体未解决问题](../optimized-sync-2026-10-31/README.md)。

### P1：补最小真实商家价值测量

v1权重30分，本报告仅给12分，是最大单项证据缺口。邀请一名真实运营，用合法可处理的一个商品任务，分别记录手工与工具的完整耗时、人工修改次数、事实错误、误报漏报、无法完成步骤和最终交付版本。保留样本数与任务条件，不以模型响应秒数替代人的工作时间，不从单例推断普遍收益。

### P1：完成最终展示材料和正式计时

r6目前仅2/10，i6与v5也受影响。制作最终海报和路演文件，围绕用户问题、两流程、一处真实风险修复、来源与未完成边界展开。比赛电脑至少做一次完整真实计时，模型等待计入总时长；不能用建议时间表代替测量结果。

### P2：用同一案例证明差异化，再验证复制

将真实记录中的“风险原句→来源依据→指定范围改稿→版本差异→带依据导出”放在一组对照中，说明通用聊天操作之外的价值。随后再用第二个合法商品或第二商家验证配置复用，记录必须重新确认的字段与失败。不要为展示效果添加假商品、假风险或假SKU。影响v2、r5及评委对产品定位的理解。

## 6. 三分钟演示目标

这是待实测的安排，不是已完成计时。模型等待和失败处理均应计入。

| 时间 | 展示内容 |
|---|---|
| 0:00–0:20 | 谁在使用、哪项重复工作；说明W101是公开真实案例 |
| 0:20–0:55 | 新品制作：材料出处、事实确认、真实生成与独立审核 |
| 0:55–1:30 | 同一文案两轮定向修改，展示原稿及两次修改结果 |
| 1:30–2:20 | 存量诊断：平台规则与宣称证据两类校验、风险批注与处理 |
| 2:20–2:45 | 版本差异、待补资料和导出；解释与同商品档案的关系 |
| 2:45–3:00 | 实际调用、来源与产品边界；历史记录明确标注日期 |

若实测超时，应调整讲解和操作安排，并向组织方核对演示要求；不省略要求的真实环节，不把预录或缓存伪装成现场。
